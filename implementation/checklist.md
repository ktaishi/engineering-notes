# 実装チェックリスト

実装とコードレビューの段階で確認するチェックリストです。
AI がコードを書く前提で、人と AI の両方が同じ観点で検証できるようにしています。AI が生成したコードでは「動く」ことと「本番で問題が起きない」ことは別なので、後者を確かめる観点を多めに入れています。

---

## 基本方針

1. **要件と設計に沿っているかを最初に確認する**
   - コードの書き方より先に、作るべきものを作っているかを確かめる
2. **テストとレビューを工程に組み込む**
   - 実装とあわせてテストを書き、実装とは別の AI にレビューさせる。人はリスクに応じて判断・確認する（詳細は [AI を前提にしたプルリクエストの判断方法](../process/ai-pr-review.md)）
3. **AI が生成したコードは、性能・セキュリティ・エラー処理を重点的に確認する**
   - 正常系は動いていても、例外時や大量データのときに問題が出やすい
4. **小さく分けて変更する**
   - 1つのプルリクエストの変更を小さく保ち、レビューと切り戻しをしやすくする

---

## チェックリスト

### 1. 要件・設計との整合

- [ ] 受け入れ条件をすべて満たしているか
- [ ] 設計（API 仕様、データモデル、処理方式）と食い違っていないか
- [ ] 要件にない機能や、不要な変更が混ざっていないか
- [ ] 仕様の変更が必要になった場合、関係者と合意したうえで設計書を更新したか

### 2. コードの品質

- [ ] 命名、構成、書き方が既存のコードの規約に沿っているか
- [ ] 同じ処理が重複していないか、既存の共通処理を使えないか
- [ ] 1つの関数・クラスの責務が大きくなりすぎていないか
- [ ] 不要なコード、デバッグ用の出力、コメントアウトしたコードが残っていないか
- [ ] フォーマッター・リンター・型チェックがすべて通っているか

### 3. エラー処理

- [ ] 入力値の検証（型、範囲、必須、文字数）をしているか
- [ ] 例外を握りつぶしていないか、ログに原因を残しているか
- [ ] 利用者に返すエラーメッセージに、内部情報（SQL、スタックトレースなど）を含めていないか
- [ ] 外部サービス呼び出しに、タイムアウト・リトライ・失敗時の扱いがあるか
- [ ] 途中で失敗したときに、データが中途半端な状態で残らないか（トランザクション）

### 4. 性能

- [ ] N+1 クエリがないか
- [ ] ループの中で DB や外部 API を呼んでいないか
- [ ] 全件取得をしていないか、ページングや件数の上限があるか
- [ ] 必要なインデックスを追加したか
- [ ] 大量データの処理は、ストリーミングやバッチ分割になっているか
- [ ] 詳細は [リリース前パフォーマンス・インフラチェックリスト](../performance/release-checklist.md) で確認する

### 5. セキュリティ

- [ ] SQL インジェクション、XSS などの対策を、フレームワークの仕組みで行っているか
- [ ] 権限の確認が、すべての API で漏れなく行われているか
- [ ] 秘密情報（API キー、パスワード）をコードやログに書いていないか
- [ ] 詳細は [セキュリティチェックリスト](../security/checklist.md) で確認する

### 6. テスト

- [ ] 正常系だけでなく、異常系・境界値のテストがあるか
- [ ] 権限のない利用者がアクセスできないことをテストしているか
- [ ] クエリ数や処理時間を確認するテストが、必要な箇所にあるか
- [ ] テストが外部環境や実行順序に依存していないか
- [ ] CI でテストがすべて通っているか

### 7. データベースの変更

- [ ] マイグレーションに、元に戻す手順があるか
- [ ] 本番のデータ量で、マイグレーションが現実的な時間で終わるか
- [ ] 大きなテーブルへの変更で、長時間のロックが発生しないか
- [ ] 既存データとの互換性（列の追加・削除・型の変更）を確認したか

### 8. AI が生成したコードの確認

- [ ] 存在しないライブラリや API、古い書き方を使っていないか
- [ ] 追加された依存パッケージが、信頼できるもので、ライセンスに問題がないか
- [ ] テストが、実装に合わせて期待値を変えただけのものになっていないか
- [ ] 指示していない箇所まで変更していないか（差分をすべて確認する）
- [ ] 例外時、大量データ時、同時実行時の動きを確認したか

### 9. ドキュメントとプルリクエスト

- [ ] API 仕様書、README、設定項目の説明を更新したか
- [ ] プルリクエストに、変更の目的、変更点、確認方法、影響範囲を書いたか
- [ ] リリース時に必要な作業（環境変数の追加、マイグレーション、データ投入など）を明記したか

## AI への依頼テンプレート

```markdown
あなたはコードレビューに詳しいエンジニアで、この変更の実装には関わっていません。
以下の変更をレビューしてください。

## 変更の目的
{ 対応する要件、受け入れ条件 }

## 差分
{ プルリクエストの差分、または対象ファイル }

## 依頼内容
1. 添付のチェックリストと照らし合わせ、問題のある箇所を洗い出してください。
2. 特に、性能（N+1、全件取得、ループ内の呼び出し）、セキュリティ（権限確認、
   入力値の検証、秘密情報）、エラー処理を重点的に確認してください。
3. 受け入れ条件を満たしているか、満たしていない場合はどこが足りないかを書いてください。
4. 不足しているテストケースを挙げてください。
5. 指摘ごとに、修正の優先度（必須・推奨・任意）と修正案を書いてください。

## 出力形式
- 指摘一覧（ファイル・行、内容、優先度、修正案）
- 不足しているテストケース
- 受け入れ条件の充足状況
```

## 人が判断すること

- [ ] AI レビューの指摘のうち、対応するもの・対応しないものの判断
- [ ] 影響範囲が大きい変更（データ移行、認証、課金など）を、人がコードまで確認したうえで、このままマージしてよいか
- [ ] 期限を優先して後回しにする改善を、記録したうえで許容するか
