# インフラ選定（AWS のサービス）

AWS で Web サービス・API を構築するときに、どのサービスを選ぶかを判断するためのノートです。
「流行っているか」ではなく、要件（性能、データ量、処理の性質）、運用の手間、費用、チームの習熟度で選ぶことを基本にしています。
サービスの機能や料金は更新されるため、採用前に必ず公式ドキュメントと料金ページで確認してください。

---

## 基本方針

1. **マネージドサービスを優先する**
   - サーバーの管理を AWS に任せられるものを優先し、運用の手間を減らす
2. **小さく始めて、必要になったら拡張する**
   - 最初から大きな構成にせず、利用者やデータの増加に合わせて段階的に強化する
3. **処理の性質に合わせて選ぶ**
   - 常に動く API、短時間で終わる処理、長時間かかるバッチで、向いているサービスが違う
4. **固定費と従量課金を意識する**
   - 常時稼働で費用がかかるもの（NAT ゲートウェイ、ElastiCache、RDS など）と、使った分だけかかるもの（Lambda、S3 など）を区別する
5. **選んだ理由を記録する**
   - 採用した理由と、採用しなかった案を残しておく

## サービスの選び方

### 1. アプリケーションの実行環境

| サービス | 向いている用途 | 注意点 |
|---|---|---|
| ECS（Fargate） | 常時動く Web API、コンテナでの開発・運用、処理時間の長いジョブ | 常時稼働のため最低限の固定費がかかる。タスク数とオートスケーリングの設計が必要 |
| Lambda | リクエストが少ない・波がある API、イベントで動く処理、短時間のバッチ | 実行時間の上限（15分）、コールドスタート、同時実行数の上限、DB 接続数の急増に注意 |
| EC2 | OS レベルの制御が必要な場合、特殊なソフトウェアを動かす場合 | OS の更新やセキュリティ対策を自分で行う必要がある |
| EKS | 大規模で、Kubernetes の知見があるチーム | 学習と運用の負担が大きい。小規模なチームでは ECS で足りることが多い |

**選び方の目安**
- まずは ECS（Fargate）か Lambda で検討する
- 常にリクエストがある API は ECS、リクエストが少ない・イベントで動く処理は Lambda が向いている
- 同じサービスの中で、API は ECS、非同期の処理は Lambda のように組み合わせてもよい

### 2. データベース

| サービス | 向いている用途 | 注意点 |
|---|---|---|
| RDS（PostgreSQL / MySQL） | 一般的な業務システム、関連の多いデータ | インスタンスクラスとストレージの設計、最大接続数、メンテナンスの時間帯 |
| Aurora | 高い可用性・性能が必要な場合、読み取りの多いサービス | RDS より費用が高くなることが多い。規模に見合うかを確認する |
| Aurora Serverless v2 | 負荷の波が大きい場合、開発・検証環境 | 最低容量の設定によっては、常時稼働の費用がかかる |
| DynamoDB | キーで取得するアクセスが中心、大量の読み書き、スキーマが柔軟なデータ | 複雑な検索や集計には向かない。アクセスのパターンを先に設計する必要がある |

**選び方の目安**
- 業務データで関連が多い場合は、RDS（PostgreSQL など）を基本にする
- 可用性や性能の要件が高くなったら、Aurora を検討する
- Lambda から接続する場合は、RDS Proxy で接続数の急増に備える

### 3. キャッシュ

| サービス | 向いている用途 | 注意点 |
|---|---|---|
| ElastiCache（Redis / Valkey） | 複数のタスクで共有するキャッシュ、セッション、ランキング | 常時稼働の費用がかかる。導入前に、ヒット率と DB 負荷の削減量を見積もる |
| ElastiCache Serverless | 負荷の予測が難しい場合、小さく始めたい場合 | 料金体系が異なるため、利用量に応じた費用を試算する |
| アプリ内キャッシュ | 小規模、タスクごとに持ってよいデータ | タスク間で共有できない |
| CloudFront | 静的ファイル、共通で返せるレスポンス | キャッシュの無効化の方法を決めておく |

### 4. ファイルの保存と配信

| サービス | 向いている用途 | 注意点 |
|---|---|---|
| S3 | 画像・ファイル・ログ・バックアップの保存 | 公開設定の誤りに注意する。ライフサイクルルールで古いデータを安い保存方式へ移すか削除する |
| CloudFront | 静的ファイルや画像の配信、Web サイトの高速化 | S3 を直接公開せず、CloudFront 経由で配信する |

### 5. 非同期処理・バッチ

| サービス | 向いている用途 | 注意点 |
|---|---|---|
| SQS | 処理の受付と実行を分ける、負荷の平準化、リトライ | 失敗したメッセージの扱い（デッドレターキュー）を決める |
| SNS | 1つのイベントを複数の宛先へ通知する | 受け取る側の失敗時の扱いを決める |
| EventBridge | イベントで処理をつなぐ、外部サービスとの連携 | イベントの形式と流れを記録しておく |
| EventBridge Scheduler | 定期実行（夜間バッチなど）の起動 | 実行の失敗を監視する |
| Step Functions | 複数の手順からなる処理、待ちや分岐のある処理 | 状態遷移の回数による料金に注意する |
| ECS のタスク実行 | 時間のかかるバッチ処理 | 処理時間の計測と、失敗時の再実行の設計が必要 |
| AWS Batch | 大量のデータを並列で処理する計算 | 一般的な Web サービスのバッチには過剰なことが多い |

**選び方の目安**
- 15分以内に終わる処理は Lambda、それより長い処理は ECS のタスクで実行する
- 夜間バッチは、EventBridge Scheduler から Lambda または ECS のタスクを起動する構成が扱いやすい

### 6. 認証

| サービス | 向いている用途 | 注意点 |
|---|---|---|
| Cognito | 利用者の登録・ログイン・多要素認証を任せたい場合 | 画面や仕様の自由度に制約がある。要件に合うかを事前に確認する |
| 外部の認証サービス・自前の実装 | 細かい要件がある場合、既存の仕組みがある場合 | 自前で実装する場合は、セキュリティの確認を十分に行う |

### 7. ネットワーク

| サービス | 用途 | 注意点 |
|---|---|---|
| VPC | ネットワークの分離 | DB などはプライベートなサブネットに置く |
| ALB | ECS などへの通信の振り分け | 常時稼働の費用がかかる |
| NAT ゲートウェイ | プライベートなサブネットから外部への通信 | 時間と通信量の両方で費用がかかる。VPC エンドポイントで費用を減らせる場合がある |
| Route 53 | ドメインの管理 | |
| WAF | 不正なアクセスの防御 | ルールの設定と、誤検知の確認が必要 |

### 8. セキュリティと秘密情報

| サービス | 用途 |
|---|---|
| IAM | 権限の管理。最小権限を基本にする |
| Secrets Manager | DB のパスワードなど、定期的に差し替える秘密情報の管理 |
| Systems Manager Parameter Store | 設定値や、秘密情報の管理（費用を抑えたい場合） |
| KMS | 暗号化の鍵の管理 |
| CloudTrail | 操作ログの記録 |
| GuardDuty | 不審な動きの検知 |

### 9. 監視

| サービス | 用途 |
|---|---|
| CloudWatch | メトリクス、ログ、アラーム、ダッシュボード |
| X-Ray | リクエストの流れと、処理時間の内訳の確認 |
| 外部の監視サービス | 複数のサービスをまとめて監視したい場合（Datadog など） |

### 10. 構築と管理

| サービス・ツール | 用途 |
|---|---|
| AWS CDK / Terraform | インフラをコードで管理し、環境を再現できるようにする |
| ECR | コンテナイメージの保存 |
| AWS Organizations | 本番・ステージング・開発でアカウントを分けて管理する |

## 構成の例

### 小規模な Web サービス（立ち上げ期）

- API：ECS（Fargate）または Lambda
- DB：RDS（PostgreSQL）
- ファイル：S3 + CloudFront
- 非同期処理：SQS + Lambda
- 夜間バッチ：EventBridge Scheduler + Lambda（15分を超える場合は ECS のタスク）
- 監視：CloudWatch
- 秘密情報：Parameter Store または Secrets Manager

### 利用者が増えてきた段階

- DB：Aurora への移行、リードレプリカの追加を検討
- キャッシュ：ElastiCache の導入を、費用対効果を見て検討
- 防御：WAF の導入
- 監視：X-Ray や外部の監視サービスで、処理時間の内訳まで追えるようにする

## AI への依頼テンプレート

```markdown
あなたは AWS のアーキテクチャに詳しいエンジニアです。
以下の要件に合う AWS の構成を提案してください。

## 要件
- サービスの概要：{ 内容 }
- 想定リクエスト数：通常 { RPS }、ピーク { RPS }
- データ量：現在 { 件数・容量 }、1年後 { 件数・容量 }
- 処理の種類：{ リアルタイムの API、非同期処理、夜間バッチなど }
- 可用性・性能の目標：{ 停止の許容時間、p95 の応答時間 }
- 予算の上限：月額 { 金額 }
- チームの状況：{ 人数、AWS の経験、運用の体制 }

## 依頼内容
1. 実行環境、DB、キャッシュ、非同期処理・バッチ、認証、ネットワーク、監視について、
   推奨するサービスと理由を挙げてください。
2. 検討したが推奨しなかった案と、その理由を挙げてください。
3. 通常時・ピーク時・1年後の月額費用の目安を、サービスごとに出してください。
4. 各サービスの上限や注意点で、この要件で問題になりそうなものを挙げてください。
5. 利用者が増えたときに、どの順番で構成を強化するかの案を出してください。
6. 料金や仕様は変わるため、公式の料金ページで確認が必要な箇所を「要確認」と書いてください。

## 出力形式
- 推奨する構成（サービス、用途、選んだ理由）
- 採用しなかった案と理由
- 月額費用の目安（サービス別、通常時・ピーク時・1年後）
- 注意点と上限
- 拡張の順番
```
