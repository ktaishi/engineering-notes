# AI 周りの情報収集

AI モデルや AI 開発ツールの情報を追いかけ、自分の開発に取り入れるためのノートです。
AI の分野は変化が非常に速く、話題になっている情報の多くは数か月で古くなります。そのため、情報を集めることよりも、「自分の作業で試して比べる仕組み」を持つことを重視しています。
情報収集の全般的な進め方は [情報のキャッチアップ方法](catch-up.md) にまとめています。

---

## 基本方針

1. **公式の発表とドキュメントで確認する**
   - モデルの性能、価格、利用条件、データの扱いは、開発元の公式情報で確かめる
2. **ベンチマークの数値より、自分の作業での結果を重視する**
   - 公開されているベンチマークは参考にとどめ、実際の案件に近い課題で試して判断する
3. **比べる仕組みを用意しておく**
   - 新しいモデルやツールが出たら、同じ課題・同じ手順で試し、これまでのものと比べる
4. **使い方の変化を、開発の流れに反映する**
   - 新しい機能や使い方は、プロンプトや開発の手順、チェックリストに反映して、チームの資産にする
5. **データの扱いと費用を必ず確認する**
   - 入力した情報が学習に使われるか、どこに保存されるか、料金体系はどうかを確認してから業務で使う

---

## 追いかける対象

| 対象 | 主な内容 | 確認する情報源 |
|---|---|---|
| AI モデル | 新しいモデルの公開、性能、価格、コンテキストの長さ、提供の終了予定 | 開発元の公式ブログ・ドキュメント・料金ページ、API の変更履歴 |
| AI 開発ツール | コーディング支援ツール、AI エージェントの新機能・設定・料金 | 各ツールの変更履歴（Changelog）、公式ドキュメント、公式ブログ |
| 開発の手法 | プロンプトの書き方、エージェントの使い方、検証の方法、開発の流れ | 開発元のガイド、実践者の技術記事・発表 |
| 周辺の仕組み | MCP などの連携の仕組み、評価・監視のツール、ライブラリ | GitHub のリポジトリとリリース、仕様のドキュメント |
| 研究の動向 | 新しい手法、評価の方法 | arXiv、Hugging Face、カンファレンスの発表 |
| ルール・リスク | 利用規約、データの扱い、法規制、セキュリティ上の注意点 | 開発元の規約・プライバシーポリシー、行政の発表、セキュリティ関連の情報 |

## 仕組みづくり

- [ ] 使っている AI モデル・ツールの、変更履歴と公式ブログを購読しているか
- [ ] API の価格改定や、モデルの提供終了（廃止予定）の告知を受け取れるか
- [ ] 自分の作業に近い「評価用の課題」をいくつか用意しているか（例：API の追加、バグの調査、リファクタリング、テストの作成、設計のレビュー）
- [ ] 評価用の課題で、品質・かかった時間・費用・手戻りの回数を記録しているか
- [ ] うまくいったプロンプトや指示の型を、記録して再利用しているか
- [ ] 試す時間を、定期的に確保しているか

---

## 新しいモデル・ツールを試すときの手順

1. **公式情報で概要を確認する**：何ができるようになったか、価格、利用条件、データの扱い
2. **評価用の課題で試す**：これまで使っているものと、同じ課題・同じ手順で比べる
3. **結果を記録する**：品質、速度、費用、手戻りの回数、気づいた癖や注意点
4. **取り入れるかを判断する**：効果が費用と移行の手間に見合うか
5. **取り入れる場合は、開発の流れに反映する**：プロンプト、設定、チェックリスト、チームへの共有

---

## 情報を判断するときの観点

- [ ] 開発元の公式情報で確認したか（噂や、デモだけの情報ではないか）
- [ ] いつの情報か（モデルやツールの更新で、すでに変わっていないか）
- [ ] ベンチマークの条件が、自分の用途に近いか
- [ ] 自分の評価用の課題で試して、効果を確かめたか
- [ ] 料金、利用制限、データの扱いが、業務で使える条件か
- [ ] 案件の契約やクライアントの規定で、利用が認められているか

---

## 業務で使うときの注意点

- 秘密情報や本番の個人情報を、AI ツールに入力しない
- クライアントの案件では、利用してよい AI ツールと、渡してよい情報の範囲を事前に確認する
- AI エージェントに与える権限（ファイル操作、コマンド実行、本番環境へのアクセス）を必要最小限にする
- AI の出力は、テストとレビューで検証してから使う（詳細は [実装チェックリスト](../implementation/checklist.md) と [セキュリティチェックリスト](../security/checklist.md)）

## 記録の例

```markdown
## { モデル・ツール名 }（{ 試した日 }）

- 試した課題：{ 例：既存 API への項目追加とテストの作成 }
- 比較対象：{ これまで使っていたもの }
- 品質：{ 修正が必要だった箇所、テストの通過状況 }
- 時間：{ 完了までの時間 }
- 費用：{ 利用料金の目安 }
- 気づいた点：{ 得意・不得意、注意すべき癖 }
- 判断：{ 取り入れる・一部で使う・見送る、その理由 }
```
